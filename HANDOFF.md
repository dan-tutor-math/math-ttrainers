# HANDOFF — полный контекст проекта «тренажёры» для новой сессии

Этот файл написан специально для того, чтобы в новой сессии Cowork (или любой другой) не пришлось ничего объяснять заново. Дай новой сессии доступ к папке `папка` на Рабочем столе (в ней лежит `тренажёры/`) — все файлы уже на месте, ничего переносить не нужно. Дальше просто попроси прочитать этот файл.

Дата последнего обновления: 27.08.2026.

---

## 1. Что это за проект

Сайт с интерактивными тренажёрами по математике (в основном под ОГЭ), лежит в папке `тренажёры/` и выложен на **GitHub Pages** (не на Cloudflare — это важно, см. раздел 8). Внутри — десятки html-файлов вида `oge*.html`, `addition.html`, `linear.html` и т. д., плюс `index.html` как общая точка входа с навигацией (вкладки «ОГЭ», «Классы», «Экзамены» и т. п.).

Поверх обычных тренажёров в последних сессиях выросли два платформенных инструмента, не привязанных к конкретному заданию:

- **«Подборка»** — можно сохранять любое задание из любого тренажёра в общий список и потом к нему возвращаться. Реализована в `index.html` + `basket-core.js`.
- **«Доски»** (`boards.html` + `boards-core.js`) — отдельный полноценный векторный вайтборд (как в GeomBoard/Notability), сейчас в разработке, на нём и сосредоточен весь этот файл.

---

## 2. Структура ключевых файлов

```
тренажёры/
├── index.html          — общая SPA-навигация по всем тренажёрам, вкладка «Подборка»
├── basket-core.js       — движок «Подборки» (общий для index.html и всех тренажёров)
├── boards.html          — разметка и стили режима «Доски» (два экрана: список досок + сам холст)
├── boards-core.js       — вся логика досок: рендер, инструменты, курсоры, экспорт в PDF и т. д. (~1700+ строк)
├── oge*.html, addition.html, linear.html, ...  — сами тренажёры (не трогали в этой сессии)
└── HANDOFF.md            — этот файл
```

Все файлы — чистый HTML/CSS/JS без сборки, без npm, открываются прямо в браузере. `boards.html` подключает `boards-core.js` обычным `<script src="boards-core.js">` в конце файла.

## 3. Как устроена платформа в целом

- Тема (светлая/тёмная) — через `data-theme` на `<html>`, набор CSS-переменных (`--bg`, `--paper`, `--grid`, `--ink`, `--pencil` и т. д.), одинаковый набор во всех файлах. Переключатель темы в правом верхнем углу — общий паттерн на каждой странице.
- В `index.html` в левом верхнем углу друг под другом — две квадратные иконки: «Подборка» (папка) и, ниже, «Доски» (иконка сетки-доски), обе `position:fixed`. Кнопка «Доски» — простая ссылка `<a href="boards.html">`, т. к. `boards.html` отдельная страница, а не часть SPA `index.html`.
- «Подборка» во всех тренажёрах имеет кнопку «В подборку» и поддерживает сортировку по времени добавления в обе стороны (кнопка-тумблер «Сначала новые» / «Сначала старые»).

## 4. Подробная история фичи «Доски» — что уже сделано

### 4.1. Первая версия (прошлая сессия, до этого файла)
Построен отдельный прототип `boards.html` + `boards-core.js` по референсным скриншотам стороннего вайтборд-приложения:
- Экран 1 — «дашборд»: папки досок + сами доски (карточки), поиск, сортировка, создание папки/доски.
- Экран 2 — сам холст: векторная модель объектов (`B.objects[]`), система камеры (`cam = {x,y,zoom}`), рендер-луп через `requestAnimationFrame`.
- Инструменты: рука (панорама), выделение, ручка (произвольная линия), ластик, прямая, кривая, четырёхугольник, многоугольник, эллипс, циркуль (окружность заданного/кликового радиуса), угол (с отображением градусов).
- Клик-модель для фигур (не drag): кликаешь точки, а не тянешь мышь — сознательный выбор ради единообразия между всеми 7 инструментами фигур и меньшего риска багов.
- Панель цвета (палитра завязана на CSS-переменные темы, поэтому чернила остаются читаемыми что на светлой, что на тёмной бумаге), толщина, пунктир, заливка, привязка к сетке (snap).
- Ластик — **векторный** (стирает объект целиком, не «частично» как ластик на растре) — сознательное упрощение.

### 4.2. Переработка листов и инструмента «рука» (прошлая сессия)
- Доска — **одно сплошное полотно**, условно разделённое полупрозрачными линиями на «листы», а не отдельные карточки с отступами. Сетка листов — 200×200 (`SHEET_COLS = SHEET_ROWS = 200`), этого достаточно, чтобы ощущаться бесконечной, но не бесконечной по-настоящему — значит, можно упереть панораму в края (`clampCam()`), а не скроллить в пустоту вечно.
- При открытии доска центрируется ровно на середину этого гигантского листа.
- Панорамирование стопорится у краёв (проверено Playwright-тестами на всех 4 направлениях).
- Убраны маленькие непонятные циферки под цветовыми кружками (счётчик использования цвета) — путали пользователя.
- Инструмент «рука»: по умолчанию **только** панорамирует, даже если жест начался прямо на фигуре (иначе рисовать было бы мучительно неудобно). Двойной клик по фигуре «взводит» её (`armedHandId`) — после этого, пока инструмент не сменили, одиночный клик именно по этой фигуре двигает её/её узлы, а клики где угодно ещё — по-прежнему панорамируют.
- Добавлена вставка изображений: файлом, буфером обмена (Ctrl+V) и перетаскиванием (drag-drop, в том числе из другой вкладки браузера). Модалка при вставке: превью, «Закрепить изображение на доске», «Привязка к сетке», «Сохранить в библиотеку» (мини-библиотека картинок на доску, `B.imageLib`).

### 4.3. Эта сессия — что доделано и исправлено

**Кнопка входа в «Доски» из index.html** — квадратная иконка под «Подборкой» в левом верхнем углу (см. раздел 3).

**Привязка изображения к сетке без люфта.** Раньше snap выравнивал только левый верхний угол картинки, а её ширина/высота могли не делиться на размер клетки — правый/нижний край съезжал с линий сетки. Теперь при включённой привязке к сетке округляются **и** позиция, **и** ширина/высота (кратно `cellSize`) — картинка ложится в клетки идеально со всех сторон.

**Закреплённое изображение теперь можно двигать.** Раньше «закрепить» блокировало и ластик, и изменение размера, и перемещение. Сейчас закрепление блокирует **только** ластик и изменение размера — перемещать по доске закреплённую картинку можно свободно через инструмент «рука» (двойной клик → взвести → тащить).

**Листы всегда идеально выровнены по сетке, размер увеличен вдвое.** Раньше размер листа (`sheetW`/`sheetH`) хранился в пикселях фиксированным числом (920×650), которое не делилось нацело на размер клетки — края листа «плавали» относительно сетки. Теперь размер листа хранится **в клетках** (`B.sheetCols`, `B.sheetRows`, стандарт 76×54 — вдвое больше по каждой стороне относительно исходных ~38×27), а фактический пиксельный размер листа всегда высчитывается как `cols * cellSize` / `rows * cellSize` — при любом изменении размера клетки (кнопки +/− в настройках) края листа гарантированно остаются точно на линиях сетки. Есть функции `sheetWpx()` / `sheetHpx()` в `boards-core.js`, замена всех старых обращений к `B.sheetW`/`B.sheetH`. Старые доски (созданные до этого изменения) мигрируются автоматически при открытии (`openBoard()`).

**Изображение: 4 угловые точки вместо одной.** Раньше можно было тянуть только за правый нижний угол. Теперь `getHandles()` для незакреплённого изображения отдаёт все 4 угла (nw/ne/se/sw), `applyHandle()` тянет по диагонали от **противоположного** угла как от неподвижного якоря, сохраняя пропорции (соотношение сторон). Работает и через инструмент «рука» (взвести двойным кликом), и через инструмент «выделение».

**Новая картинка по умолчанию не закреплена.** В модалке вставки чекбокс «Закрепить изображение» теперь по умолчанию выключен — сразу после вставки картинку можно подвинуть и растянуть, закрепление — осознанное действие уже потом, кнопкой на нижней панели инструментов.

**Кнопка «Закрепить/Открепить» в нижней панели — теперь настоящий тумблер.** Раньше кнопка была видна только когда картинка закреплена (и всегда означала «открепить»). Теперь кнопка видна для **любого** выделенного изображения (закреплённого или нет), тёмный фон = сейчас закреплено, без фона = сейчас свободно, клик переключает состояние в обе стороны. Замочек, который раньше рисовался прямо поверх картинки на холсте (иконка 🔒 в углу изображения), убран — состояние показывает только кнопка на панели.

**Зум-колонка: плюс и минус поменяны местами.** Теперь сверху вниз: `+`, `100%`, `−` (было наоборот — выглядело неестественно).

**Экспорт в PDF («Сохранение конспекта»).** Верхняя кнопка «расширения» (которая раньше была «показать весь лист») заменена на кнопку «Сохранить в PDF» (иконка документа, id `railPdf`). Открывает модалку:
- Сохраняются **только** листы, на которых реально что-то нарисовано или вставлено (пустые и стёртые в конспект не попадают) — это вычисляет функция `findContentSheets()`: находит bounding box всех объектов на доске, определяет диапазон затронутых листов и проверяет пересечение каждого листа с объектами.
- Предпросмотр листов по одному, кнопки «‹»/«›», подпись «Страница X из N».
- Тумблер «Включить страницу в конспект» на каждой странице (можно вручную исключить конкретный непустой лист).
- **Порядок страниц** — «По ширине» (слева направо, ряд за рядом) или «По высоте» (сверху вниз, столбец за столбцом, для тех кто листает бесконечной лентой). Настройка живёт прямо в этой модалке (изначально была в настройках размера клетки — перенесли сюда по просьбе пользователя, т. к. по смыслу она относится именно к экспорту). Переключение на лету пересобирает список страниц (`refreshPdfPagesOrder()`), стараясь остаться на том же листе, что был в фокусе.
- Генерация через **jsPDF**, подключённый через `<script src="https://cdnjs.cloudflare.com/ajax/libs/jspdf/2.5.1/jspdf.umd.min.js">` в `boards.html`.
- Каждая страница рендерится в оффскрин-канвас через существующую функцию `render()` (тот же приём, что и в обычном PNG-экспорте одного листа) и кладётся в PDF как **JPEG** (не PNG!) с качеством 0.88 — специально, чтобы конспект из полусотни листов не весил сотни мегабайт (проверено: страница с рисунком раньше весила ~67 МБ на PNG, стала ~0.5 МБ на JPEG). Перед рендером оффскрин-канвас заранее заливается цветом бумаги (`--paper`), чтобы редкие выступы рисунка за пределы мирового 0..totalW/H не превращались на JPEG в чёрные пиксели (у JPEG нет прозрачности).
- Функции: `openPdfModal()`, `closePdfModal()`, `updatePdfModalUI()`, `renderSheetThumb()`, `objectBBox()`, `findContentSheets()`, `sheetKey()`, `refreshPdfPagesOrder()`.

**Панорамирование средней кнопкой мыши.** Раньше пан работал только правой кнопкой (или левой с Alt). Добавлена проверка `e.button === 1` в обработчике `pointerdown`.

**Свой курсор под каждый инструмент, вместо одного крестика на всё.** Реализовано через `canvas.style.cursor = 'url(data:image/svg+xml,...) hotspotX hotspotY, fallback'`:
- **Перо** — нарисованная вручную SVG-иконка наклонённой ручки (корпус светлый с тёмной обводкой — виден на любом фоне листа что в светлой, что в тёмной теме; кончик/нибу подкрашен ровно в `resolveColor(curColorTok)` — текущий цвет чернил). Функция `penCursorCSS()`. Пересчитывается при: смене инструмента, смене цвета (внутри `renderSwatches()`), смене темы (хук в инлайн-скрипте переключателя темы в `boards.html`).
- **Ластик** — своя SVG-иконка (розовый ластик), функция `eraserCursorCSS()`.
- **Рука** — нативный `cursor: grab`, во время активного перетаскивания меняется на `grabbing` и возвращается обратно при отпускании кнопки мыши.
- **Выделение** — нативная стрелка (`cursor: default`).
- **Линия / кривая / четырёхугольник / многоугольник / эллипс / циркуль / угол** — нативный `cursor: crosshair` (прицел теперь только у инструментов точной расстановки точек, не у всех подряд).
- Общая функция `updateCursor()` вызывается: при клике по инструменту в доке, при открытии доски (`openBoard()`), при смене цвета, при смене темы, при завершении панорамирования.

Всё это проверено сквозными Playwright-тестами (headless Chromium в песочнице с ручной подгрузкой недостающих системных библиотек через `apt-get download` + `dpkg-deb -x`, т. к. в песочнице нет root) — на каждом шаге 0 ошибок в консоли.

## 5. Модель данных досок (как это устроено СЕЙЧАС — только localStorage)

Всё хранится в `localStorage` браузера под ключом **`ogeBoards:v1`**. Значение — JSON:

```js
DB = {
  folders: [ { id, name, createdAt } ],
  boards: [
    {
      id, name,
      folderId,               // null или id папки, либо '__recent'
      createdAt, updatedAt, lastOpenedAt,
      cellSize: 24,            // px на клетку, шаг регулировки ±4, диапазон 12..64
      sheetCols: 76, sheetRows: 54,   // размер ОДНОГО листа в клетках (не в пикселях!)
      pageOrder: 'h',           // 'h' (по ширине) | 'v' (по высоте) — влияет на порядок PDF-экспорта
      objects: [ /* штрихи, фигуры, картинки — плоский список */ ],
      recentColors: [ /* последние использованные цвета, токены или hex */ ],
      colorUsage: { /* больше не отображается пользователю, оставлено для обратной совместимости */ },
      imageLib: [ { id, src, createdAt } ],  // мини-библиотека вставленных картинок этой доски
    },
  ],
}
```

Объект на доске (`B.objects[i]`) — один из типов: `pen`, `line`, `curve`, `quad`, `poly`, `ellipse`, `circle`, `angle`, `image`. У каждого своя форма (`points[]`, плюс специфичные поля вроде `rx/ry` у эллипса, `r` у циркуля, `ctrl` у кривой, `w/h/natW/natH/src/locked` у картинки). Цвет хранится либо как **имя CSS-переменной** (`'--pencil'`), либо как литеральный hex, если пользователь выбрал свой цвет — резолвится в реальный цвет через `resolveColor(tok)`.

Сохранение — `saveDB()` с debounce 300 мс + принудительная синхронная запись на `beforeunload` и `visibilitychange`, чтобы не терять последние правки при закрытии вкладки.

**Важно:** это чисто локальное хранилище одного браузера на одном устройстве. Никакой синхронизации между устройствами и никакой многопользовательности сейчас нет — это и есть тема следующего этапа (раздел 7).

## 6. Технические детали реализации (для быстрой ориентации в коде)

- Мировые координаты объектов не зависят от зума/панорамы. Перевод мир↔экран — `worldToScreen()` / `screenToWorld()` / `eventWorld(e)`.
- Камера — `cam = {x, y, zoom}`, диапазон зума `ZOOM_MIN=0.1..ZOOM_MAX=4`.
- Для PNG/PDF-экспорта используется отдельный слой косвенности `activeCam` — на время оффскрин-рендера подменяется «виртуальная камера» (`fakeCam`), не трогая боевую `cam`, чтобы после экспорта картинка на экране не дёрнулась.
- `render(c, w, h, camv, isScreen, renderDpr)` — общая функция рендера, используется и для живого канваса, и для оффскрин-экспорта (флаг `isScreen` отличает «это то, что видит пользователь» от «это рендерится в файл», плюс от него зависит, обновлять ли UI-элементы типа кнопки открепления).
- Undo/redo — простой стек JSON-снапшотов всего `B.objects` (`undoStack`/`redoStack`, лимит 60 шагов), не операционный, не per-user — это тоже придётся переосмыслить для совместного режима (см. раздел 7, пункт про undo).
- Хиттесты объектов — `hitTestObject()` (для клика/ластика), `hitTestHandles()` (для ручек изменения размера/формы), допуски считаются в мировых единицах с поправкой на текущий зум (`8/cam.zoom`, `14/cam.zoom` для ластика).

## 7. СЛЕДУЮЩИЙ ЭТАП — план облачной синхронизации и совместного режима (пока НЕ реализовано, только обсуждено и согласовано)

Пользователь (владелец платформы) хочет:

1. **Заходить в свои доски с любых устройств** — сейчас невозможно, всё в localStorage одного браузера.
2. **Давать доступ другим преподавателям.**
3. **Совместное рисование в реальном времени с учеником** на одной доске — оба видят правки друг друга мгновенно.
4. **Только онлайн-режим** для совместных досок — никаких локальных копий и связанных с ними конфликтов; если сети нет — доска просто не работает (инструменты недоступны), пока связь не восстановится. Отдельный настоящий офлайн-режим (PWA) — возможная, но отдельная и отложенная задача, не блокирующая текущий план.

### 7.1. Согласованная модель ролей и доступа
Обсуждено и **явно подтверждено пользователем** (через выбор вариантов):

- **Роли:** владелец (сам пользователь) → преподаватели → ученики.
- **Преподаватели** получают доступ через **самостоятельную регистрацию по приглашению** (не «владелец вручную создаёт токен и пересылает», а полноценная форма регистрации по ссылке-приглашению).
- **Что видит преподаватель, которому дали доступ:** «Общее + личное у каждого» — то есть общее пространство досок/папок, видимое всем преподавателям с доступом, **плюс** у каждого преподавателя есть свои личные доски, которые не видны ни другим преподавателям, ни даже владельцу.
- **Доступ ученика к конкретной совместной доске:** ученик может **самостоятельно зарегистрироваться как ученик**, а доступ к конкретным доскам получает **по ссылкам-приглашениям** — на каждую доску своя ссылка, доступ накапливается (сколько ссылок открыл/активировал — к стольким доскам и есть доступ).

### 7.2. Архитектура (обсуждён и скорректирован выбор технологий — см. раздел 8 про хостинг)
Изначально обсуждали Cloudflare (Workers + D1 + Durable Objects), но после решения переезжать на российскую платформу (раздел 8) архитектура упростилась и стала даже понятнее:

- **Backend:** обычный постоянно работающий Node.js-сервер (Express/Fastify) — НЕ классический serverless с таймаутом, потому что нужны долгоживущие WebSocket-соединения.
- **База данных:** PostgreSQL (managed, через хостинг-провайдера).
  - Таблицы: `users` (id, role: owner/teacher/student, name, email?, password_hash, created_at), `invites` (код приглашения, какую роль даёт, кем создан, кем использован, срок действия, `board_id` — для точечных ученических приглашений на конкретную доску), `boards` (id, name, owner_id, folder_id, флаг «общая» или «личная»), `board_access` (many-to-many: board_id ↔ user_id — кто именно из учеников/преподавателей имеет доступ к какой доске), `folders` (id, name, owner_id, is_common).
- **Живое совместное рисование:** WebSocket-«комната» на каждую доску (в памяти Node-процесса — обычный `Map<boardId, Set<WebSocket>>`, никакого Durable Objects не нужно, это его прямая функциональная замена, но проще). Каждое действие на доске (новый штрих, фигура, перемещение/удаление объекта, вставка картинки) рассылается всем, кто сейчас подключён к этой же доске. При подключении нового участника ему сразу отправляется текущее полное состояние доски.
- **Содержимое досок** при таком подходе хранится либо прямо в Postgres (JSON-колонка — самый простой вариант, почти не меняет текущую модель данных из раздела 5, просто переносит тот же JSON с клиента на сервер), либо в отдельном файлохранилище/S3, если объём вырастет — для старта достаточно JSON-колонки в Postgres.

### 7.3. Что нужно переделать на фронтенде (`boards-core.js` / `boards.html`)
- Экраны логина/регистрации (для преподавателя — по ссылке-приглашению; для ученика — самостоятельная регистрация + отдельно активация ссылок-приглашений на конкретные доски).
- Список досок на дашборде — вместо чтения `DB` из `localStorage` теперь запрос к API (`GET /api/boards`), с разделением на «общие» и «мои личные» у преподавателей.
- Открытие доски = обязательное WebSocket-подключение; пока соединения нет — инструменты рисования недоступны/затемнены, никакой работы «начерно локально».
- Каждое действие (`pushUndo()` + добавление в `B.objects` + `saveDB()`) переделывается в: применить локально сразу (чтобы не было задержки на своём экране) **и** отправить операцию по сокету остальным участникам; входящие операции от других участников применяются точно так же к локальному `B.objects`.
- **Undo/redo в совместном режиме** — открытый вопрос, требует решения перед реализацией: скорее всего, каждый участник должен отменять только свои собственные последние действия, а не действия другого человека (как это устроено, например, в Figma) — нынешний общий стек `undoStack`/`redoStack` на всю доску для этого не годится, его придётся переделать в персональный стек операций на пользователя.
- Бонус, который легко добавить раз уже есть живое соединение: показывать курсор/имя другого участника прямо на доске в реальном времени (presence).

### 7.4. Предложенный план по фазам (ещё не начат)
1. **Фаза 1** — аккаунты и авторизация (регистрация владельца/преподавателей, вход), доски переезжают из `localStorage` в серверную базу — уже даёт кросс-девайсность и разделение общее/личное, но пока БЕЗ live-соединения (просто как обычное сохранение на сервер вместо localStorage).
2. **Фаза 2** — совместное рисование в реальном времени через WebSocket-комнаты (раздел 7.2–7.3).
3. **Фаза 3** — регистрация учеников, ссылки-приглашения на конкретные доски, курсор/имя другого участника на доске, панель управления доступом для владельца (кому что видно, отзыв доступа).

## 8. Решение по хостингу (обсуждено и согласовано)

Изначально обсуждался Cloudflare (Workers + D1 + Durable Objects). Пользователь попросил **российскую платформу**, которая работает без VPN — основная причина: оплата и доступность из России без дополнительных сложностей.

Точного клона связки «Workers + D1 + Durable Objects» в России нет, но вся нужная функциональность закрывается более простой и даже более портируемой связкой (см. раздел 7.2): **Node.js-сервер + WebSocket + PostgreSQL**, которая не привязана к проприетарным примитивам конкретного облака.

**Рекомендация: Timeweb Cloud.**
- Cloud Apps — деплой прямо из GitHub/GitLab-репозитория, без ручной возни с сервером.
- Поддерживает Node.js, держит долгоживущие WebSocket-соединения (это обычный постоянно работающий процесс, а не serverless-функция с таймаутом — совместное рисование ложится сюда естественно).
- Managed-базы данных (Postgres/MySQL/Redis) от ~230 ₽/мес с бэкапами.
- S3-хранилище + CDN для статики (можно и тренажёры туда же перенести).
- Российское юрлицо, оплата российской картой, без VPN.

**Альтернатива: Yandex Cloud** — есть готовый официальный пример именно serverless-приложения на WebSocket, своя база YDB или managed Postgres/MySQL. Мощнее и «энтерпрайзнее», но настройка длиннее (Cloud Functions + API Gateway + IAM-роли собираются по отдельности, а не одним деплоем репозитория, как у Timeweb).

**Для масштаба этого проекта (несколько преподавателей, ученики, невысокая нагрузка) выбор пал на Timeweb Cloud** — быстрее собрать, проще потом поддерживать.

### 8.1. Алгоритм переноса (согласован, но с одним открытым вопросом — см. раздел 9)
1. Завести аккаунт на Timeweb Cloud, поднять Cloud Apps-проект и managed Postgres.
2. **Тренажёры** (сейчас на GitHub Pages) — подключить тот же git-репозиторий к статическому хостингу/CDN Timeweb, перевести DNS домена (если есть свой домен) с GitHub Pages на Timeweb. Файлы не меняются вообще.
3. Backend для досок (аккаунты, приглашения, доски, WebSocket-комнаты — раздел 7) — отдельный Node.js-репозиторий, деплой вторым Cloud Apps-сервисом, прогнать миграцию схемы в managed Postgres.
4. **Расписание** (у пользователя уже есть отдельный инструмент-расписание с редактированием и сохранением через Cloudflare) — перенос требует уточнения, что именно там используется на Cloudflare (см. раздел 9). Проект расписания физически НЕ находится в папке `папка/` (проверено — там его нет), значит для точного плана переноса нужен либо доступ к его репозиторию/папке, либо описание пользователем того, что там сейчас используется (Workers? Pages? D1? KV? Durable Objects?).
5. Погонять новое параллельно со старым, не отключая старое сразу; убедиться, что всё работает; только потом переключить DNS и решить судьбу старого Cloudflare-аккаунта.
